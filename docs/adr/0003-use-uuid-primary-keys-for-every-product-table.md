# 0003. Use UUID primary keys for every product table

* **Status**: accepted
* **Date**: 2026-08-23
* **Deciders**: Project Amanah team

## Context and Problem Statement

`rules/database.md` states that every table must have a single-column surrogate
primary key, and that the default for a single-database system is
`bigint GENERATED ALWAYS AS IDENTITY` — it is compact, sequential, and does not
fragment indexes. The same section carves out an exception: identifiers exposed
outside the database should be time-ordered UUIDs or ULIDs, and warns that random
UUIDv4 keys fragment indexes on large tables.

`spec.md` section 14 requires UUID primary keys, and `AGENTS.md` requires UUIDs
for persisted public identifiers. Almost every identifier in this schema appears
in a URL (`/v1/items/{id}`), in an API response, or in a report citation.

The two documents therefore have to be reconciled explicitly rather than by
picking whichever was read last.

## Decision Drivers

* Sequential identifiers exposed in URLs are enumerable. `rules/security.md`
  requires that guessable identifiers never be exposed without a per-request
  authorization check, and prefers indirect references or UUIDs.
* Every table here is reachable from an API path or a stored citation, so a
  public/internal key split would mean two keys on nearly every table.
* Supabase runs PostgreSQL 17 with `gen_random_uuid()` available in core. The
  `pg_uuidv7` extension that would give time-ordered keys is not installed on the
  managed platform.
* Expected volume for this project is in the millions of rows at most, not the
  hundreds of millions where UUIDv4 index fragmentation becomes the dominant
  cost.

## Considered Options

* `bigint GENERATED ALWAYS AS IDENTITY` everywhere, with a separate public UUID
  column on the tables the API exposes.
* Random UUIDv4 primary keys generated by `gen_random_uuid()`.
* Time-ordered UUIDv7 primary keys via `pg_uuidv7`.

## Decision Outcome

**Chosen option**: random UUIDv4 primary keys, generated in Postgres with
`gen_random_uuid()` as a column default.

Generation stays in the database rather than in the application, so a row written
by a migration, by an importer, or through the ORM is keyed the same way.

This is a deliberate, documented departure from the `bigint IDENTITY` default in
`rules/database.md`, taken under that file's own exception for externally exposed
identifiers.

### Positive Consequences

* No product identifier is enumerable, so a caller cannot walk `/v1/items/1`,
  `/v1/items/2` and learn how much data exists or that a record they cannot read
  is there.
* One key per table. A separate internal key and public key on twenty-one tables
  would double the join surface and create a class of bug where the wrong one is
  published.
* Identifiers can be generated before insert where a later step needs one, which
  matters for the checkpoint-then-enqueue pattern the collection pipeline uses.

### Negative Consequences / Trade-offs

* Random UUIDs insert at random positions in the primary-key B-tree, so index
  pages fragment and write amplification is higher than with sequential keys.
  This is the cost `rules/database.md` warns about; it is accepted at this
  project's expected volume and re-examined if `content_items` approaches a
  hundred million rows.
* Keys are 16 bytes rather than 8, which enlarges every index that carries one.
* Primary-key order is not insertion order, so no query may treat `id` as a proxy
  for time. Ordering is always by an explicit `<event>_at` column, with `id`
  used only as the tie-breaker that makes a cursor page's ordering total.
